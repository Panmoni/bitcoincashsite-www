## Summary

"This proposal makes Pay to Script (P2S) outputs standard and increases the length limits on token commitments and
standard unlocking bytecode." See [P2S](/glossary#p2s).

A P2S output puts the contract's locking bytecode directly in the output, with no hash wrapper. It has no address that a
normal wallet can pay by mistake.

## Motivation

- **Wallet safety.** Many contracts should not be "randomly payable." Every P2SH contract has a payable address, so
  confused users can send funds to places they can never recover. P2S gives contract authors a primitive that is "both
  more byte efficient and safer for end users."
- **Simpler contracts.** Covenants no longer need to build and check a P2SH hash for each output, then unpack it at
  spend time. The CHIP says this cuts at least 34 bytes of overhead per output for most covenant systems.
- **Room to grow.** Longer NFT commitments and unlocking bytecode serve vaults, multi-party covenants and DeFi apps.

## What it specifies

- **Standard outputs.** The list of allowed output templates (P2PK, P2PKH, P2SH20, P2SH32, `OP_RETURN`, bare multisig)
  is replaced by a length check: locking bytecode up to 201 bytes is standard. Longer bytecode is standard only if it is
  a valid `OP_RETURN` data output within the existing cumulative 223-byte limit.
- **Token commitments:** maximum length raised from 40 to 128 bytes. This is a consensus change to
  [CashTokens](/chips/chip-2022-02-cashtokens).
- **Unlocking bytecode:** the 1,650-byte standard limit is removed, so standard and consensus limits match at 10,000
  bytes.
