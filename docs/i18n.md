# Localized content

How translated words are stored, found and shown. The locale list and
routing live in `src/i18n/locales.ts` (PAN-376); UI strings live in the
message catalog (PAN-377). This page covers content: collections, page prose
and the JSON data files.

## Where translations live

| What | English | Translation |
|---|---|---|
| Collections (`post`, `upgrades`, `chips`, `compare`, `guides`, `reference`, `reports`) | `src/content/<collection>/<slug>.md` | `src/content/<collection>/<locale>/<slug>.md` |
| Page prose | `src/content/pages/<page>.yaml` or `.md` | `src/content/pages/<locale>/<page>.yaml` or `.md` |
| JSON data (`glossary`, `opcodes`, `projects`) | `src/data/<file>.json` | `src/data/i18n/<locale>/<file>.json` |

English stays at the collection root, so English ids and URLs never change.
Each English loader in `src/content.config.ts` skips the locale dirs. The
translations load into a parallel `<collection>L10n` collection (`chipsL10n`,
`pagesL10n`, …) whose ids are `<locale>/<slug>`, so they cannot collide with
an English id.

## Translation metadata

Every translated entry carries a `translation` block in its frontmatter (or
at the YAML top level). It is nested so it cannot clash with an entry's own
fields: chips and upgrades already have a `status`.

```yaml
translation:
  sourceHash: 94c72a8ec3bfeba7
  status: machine
  translator: Claude
```

| Field | Meaning |
|---|---|
| `sourceHash` | `hashSource()` of the English source file it was translated from: 16 hex chars of its SHA-256 |
| `status` | `machine` (a draft nobody has checked) or `reviewed` |
| `translator` | who or what made it |
| `reviewer` | who checked it; required when `status` is `reviewed` |

Zod checks all of it at build: a translation without `sourceHash` fails the
build. A translation never sets `lang`; its language is its locale dir, and
the build rejects a `lang` field there. On an English-root entry `lang` names
the language it was written in, which is not always English: the Venezuela
guide is a Spanish original served at `/guides/venezuela`.

When the English source changes, its hash no longer matches the
translation's `sourceHash`, and the translation is stale.

## Finding a translation

`getLocalizedEntry(collection, slug, locale)` in `src/utils/l10n.ts` returns
the entry in that locale, or `null`. It never substitutes English; the
caller decides what `null` means. Pages read their copy through
`getPageCopy(id)` / `getPageEntry(id, locale)` in `src/utils/pages.ts`.

## Fallback policy

- **A whole page is never served in English at a locale URL.** No locale
  entry means no locale route: a locale's `getStaticPaths` lists only the
  slugs `getLocalizedEntry` finds. Astro's i18n `fallback` stays off.
- **An embedded fragment may fall back to English**, for example a glossary
  definition inside a Spanish page whose overlay lacks it. It must render
  inside an element with `lang="en"` and `data-l10n-fallback`, which
  `<LocalizedText>` (`src/components/common/LocalizedText.astro`) does for
  every value from `localizeRecord()`. The i18n check lists every
  `data-l10n-fallback` element in `dist`, so each fallback is visible.

`/es/prueba-i18n` is the fixture: it embeds the untranslated glossary term
`utxo`, which renders as `<span lang="en" data-l10n-fallback>`.

## Page prose

A file in `src/pages/` holds layout and component calls. Its words live in
`src/content/pages/<id>.yaml` (structured props: headings, item lists,
calls to action) or `<id>.md` (long prose such as the legal pages), where
`<id>` is the page path with dashes (`chips/index.astro` → `chips-index`).
Text with inline links or emphasis is an HTML string, rendered with
`set:html`. Item arrays move whole, icons and links included, so a
translator copies the file and changes only the words.

## JSON overlays

`src/data/i18n/<locale>/<file>.json` holds only translatable fields, keyed
by the English record's `id`:

```json
{
  "utxo": {
    "definition": { "text": "Salida de transacción no gastada…", "sourceHash": "3f1c…" }
  }
}
```

`sourceHash` is `hashSource()` of that English field's value. The overlay
never holds untranslatable data, so the daily refresh
(`.github/workflows/refresh-data.yml`) never reads or writes it.
`localizeRecord(record, file, fields, locale)` merges it: a record or field
with no overlay keeps its English text, marked as a fallback fragment, so a
project the refresh adds tomorrow shows in English until someone translates
it.

## Orphans

A translation whose English id no longer exists is an orphan: left alone, it
would attach to whatever later reuses that id. `findOrphans()` in
`src/utils/localize.mjs` lists every content translation and overlay id
with no English original. The CI check that runs it is a separate issue.
